# Model Review Skill

## Mission

对已有的业务经验模型进行审阅、验证和完善，确保：
- 模型准确反映用户的实际工作方式
- 关键业务对象和信息完整无遗漏
- 对象间的关联关系合理一致
- 处理规则和状态流转符合实际
- 约束条件完整记录

**核心原则**：我们是业务的"镜子"，反射用户的真实工作方式，不是设计师。审阅标准是"这是否准确描述了你的实际工作"。

## Input Context

本技能在以下情况触发：
1. 用户明确要求进入审阅模式
2. `output/business-model.json` 已存在且包含 entities（系统自动判断）
3. 用户完成 Phase 2 业务精炼后想回顾和修改模型

输入来源：读取 `output/business-model.json` 获取当前完整的业务模型。

**注意**：由于业务模型是增量式构建的，审阅时可能已经包含相当完整的信息（实体、属性、关系、规则），也可能只有初步的框架。根据实际内容灵活处理。

## Approach

### 审阅策略

采用**主动审阅 + 被动响应**相结合的方式：
1. **主动审阅**：自动检查模型的完整性、一致性，提出改进建议
2. **被动响应**：根据用户的意图执行查看、修改等操作

### Step 1: 智能审阅与展示

首先对模型进行智能审阅，然后向用户展示。

#### 1.1 自动质量检查

在展示前，自动检查以下维度：

**完整性检查**：
- 每个业务对象是否都有详细的信息列表？
- 是否有关键对象缺少关联关系描述？
- 是否有对象缺少状态流转或处理规则？
- 是否存在"待澄清"的问题未解决？

**一致性检查**：
- 关联关系是否双向一致？（如：订单→产品是一对多，产品→订单是否对应？）
- 状态流转是否有断点？（如：有"生产中"但没有说明如何进入该状态）
- 约束条件是否与处理规则冲突？
- 必填信息是否在相关规则中被引用？

**合理性检查**：
- 是否有孤立对象（与其他对象无任何关联）？
- 是否有循环依赖？
- 状态流转是否符合常理？（如：是否有"已完成"回到"新建"的情况，如果有，原因是什么？）

#### 1.2 展示模型

用业务语言展示模型的核心内容：

```markdown
## 业务模型概览

我已根据你的工作经验整理了业务模型。在展示之前，我先做了一些检查：

**✓ 完整性**：{检查结果，如"所有6个业务对象都有详细信息"}
**✓ 一致性**：{检查结果，如"发现1处需要确认的关联关系"}
**⚠ 待完善**：{发现的问题，如"生产任务缺少状态流转描述"}

---

### 关键业务对象
- **{对象1}**: {简要说明}，包含 {数量} 项信息
- **{对象2}**: {简要说明}，包含 {数量} 项信息
...

### 对象间的关联
- {对象A} ↔ {对象B}: {关联描述}
...

### 核心业务流程
{简述主要业务流程}

### 需要注意的地方
{列出审阅中发现的问题或需要确认的点}
```

### Step 2: 询问用户意图

展示后，提供清晰的操作选项：

**可选操作**：
1. **查看详情** - 深入了解某个对象或关系的细节
2. **修改调整** - 修正错误、补充遗漏、调整关系
3. **补充完善** - 添加新的对象、规则或约束
4. **重新梳理** - 对某个部分重新进行深度挖掘
5. **确认完成** - 模型无误，结束建模

**询问方式**：
- "以上是模型的概览。你想做什么？可以：查看详情、修改调整、补充完善，或者确认完成。"
- "我发现了几个可能需要确认的地方（见上方'需要注意的地方'），你想先看看这些吗？"

### Step 3: 根据选择执行操作

#### 选项 A: 查看详情

用户想深入了解模型的某部分。

**引导方式**：
- "你想查看哪个部分？可以说：'{对象名称}的详细信息'、'{对象A}和{对象B}的关联'、'订单的处理规则'等"
- 或者直接列出可查看的部分供选择

**展示逻辑**：
- 从模型中提取用户询问的部分
- 用业务语言清晰展示
- 展示后询问："这部分符合你的实际情况吗？有需要调整的吗？"

#### 选项 B: 修改调整

用户想修正模型中的错误或调整内容。

**支持的修改类型**：

1. **修改对象信息**
   - 增加信息："给【订单】增加一个【优先级】字段"
   - 删除信息："订单不需要记录【传真号码】"
   - 修改信息："【交付日期】应该是必填的，不是可选的"

2. **调整关联关系**
   - "一个客户只能有一个订单，不是多个"
   - "订单和生产任务是一对一，不是一对多"

3. **修正处理规则**
   - "排产时不仅看交付日期，还要考虑客户等级"
   - "质检不合格不是退回生产，而是直接报废"

4. **调整状态流转**
   - "订单状态中应该增加'已取消'状态"
   - "生产中可以直接跳到已交付，不需要经过质检"

5. **修改约束条件**
   - "订单金额可以为零（样品单）"
   - "交付日期可以早于下单日期（补录历史订单）"

## 修改流程

所有模型修改都必须立即写入文件，执行以下步骤：

1. 确认修改内容："你是想把【订单】的【收货地址】从可选改为必填，对吗？"
2. 调用 `read_file({ filePath: "output/business-model.json" })` 读取当前内容
3. 在内存中修改对应字段
4. 调用 `write_file({ filePath: "output/business-model.json", content: "<完整 JSON>" })` 写回
5. 调用 `write_file({ filePath: "output/interview-progress.md", content: "<更新摘要>" })`
6. 调用 `write_file({ filePath: "MEMORY.md", content: "<更新后的记忆>" })`
7. 用业务语言告知结果："已调整。【订单】的【收货地址】现在是必填项。"
8. 询问是否继续："还有其他需要调整的吗？"

### 选项 C: 补充完善

用户想添加模型中遗漏的内容。

**引导方式**：
- "你想补充什么？可以是：新的业务对象、新的处理规则、新的约束条件，或者其他遗漏的内容"
- "根据我的检查，以下内容可能需要补充：{列出审阅中发现的缺失}"

**补充类型**：

1. **新增业务对象**
   - 询问对象名称和含义
   - 询问包含哪些信息
   - 询问与其他对象的关联
   - 询问处理规则和状态流转

2. **新增处理规则**
   - "在什么情况下会用到这条规则？"
   - "具体的判断标准是什么？"
   - "有没有例外情况？"

3. **新增约束条件**
   - "这个限制适用于哪些场景？"
   - "如果违反了会怎样？"

4. **补充状态流转**
   - "从【状态A】到【状态B】的触发条件是什么？"
   - "有没有其他可能的流转路径？"

#### 选项 D: 重新梳理

用户对某个部分不满意，想重新深度挖掘。

**引导方式**：
- "你想重新梳理哪个部分？比如'订单的完整流程'、'生产任务的排产逻辑'等"
- "我会像之前一样，通过对话重新深入了解这部分内容"

**执行流程**：
1. 确定重新梳理的范围
2. 回到类似 `business-refinement` 的深度追问模式
3. 针对该部分进行详细探索
4. 更新模型中的相应内容
5. 展示更新后的结果

#### 选项 E: 确认完成

用户认为模型已经完善，准备结束建模。

**最终确认清单**：

在结束前，请确认以下几点：

```
✓ 所有关键业务对象都已识别并详细描述
✓ 每个对象的信息完整准确（包括必填/可选标记）
✓ 对象之间的关联关系符合实际情况
✓ 处理规则准确描述了你的判断标准和决策逻辑
✓ 状态流转完整反映了实际工作流程（包括异常处理）
✓ 约束条件已全部记录
✓ 没有遗留的"待澄清"问题
```

**如果有未完成项**：
- "我发现还有以下问题未解决：{列出}"
- "这些问题需要在完成前澄清吗？还是可以暂时保留？"

**完成消息**：
```
太好了！你的业务经验已成功沉淀为结构化的业务模型。

这个模型记录了：
- {数量} 个关键业务对象
- {数量} 条关联关系
- {数量} 条处理规则
- {数量} 个状态流转路径
- {数量} 个约束条件

接下来，我们可以基于这个模型探索如何用 AI 技术优化你的工作流程。

感谢你的耐心配合！
```

## 智能审阅规则

在审阅阶段，自动应用以下检查规则：

### 完整性检查规则

1. **对象完整性**：每个业务对象应有：
   - 至少 3 项信息（除非确实很简单）
   - 至少 1 个关联关系（除非是独立对象）
   - 处理规则或状态流转（至少其一）

2. **关联完整性**：
   - 如果 A→B 有关联，B→A 也应有对应描述
   - 关联应有明确的数量关系（一对一、一对多等）

3. **状态流转完整性**：
   - 应有明确的起始状态和结束状态
   - 每个中间状态应有进入和离开的路径
   - 异常情况应有处理路径

### 一致性检查规则

1. **关联一致性**：
   - 如果"一个客户有多个订单"，则"一个订单属于一个客户"
   - 数量关系应对称合理

2. **规则一致性**：
   - 处理规则不应与约束条件冲突
   - 必填信息应在相关规则中被使用

3. **状态一致性**：
   - 状态名称应统一（不要混用"进行中"和"生产中"指代同一状态）
   - 状态流转不应有死循环（除非有明确的退出条件）

### 合理性检查规则

1. **孤立对象检查**：
   - 标记与其他对象无任何关联的对象
   - 询问是否真的独立，还是遗漏了关联

2. **循环依赖检查**：
   - 检测 A→B→C→A 的循环
   - 如果有，确认是否合理（有些循环是正常的）

3. **常识检查**：
   - 交付日期不应早于下单日期（除非有特殊说明）
   - 数量不应为负数
   - 必填信息不应在某些规则中被忽略

## 术语指南

**永远使用业务语言，避免技术术语：**

| 不要说 | 要说 |
|--------|------|
| 实体/属性 | 业务对象 / 包含的信息 |
| 关系/基数 | 联系 / 关联 / 一个对应几个 |
| 业务规则 | 处理方式 / 判断标准 |
| 生命周期/状态机 | 流转过程 / 状态变化 |
| 约束/不变量 | 限制条件 / 必须满足的要求 |
| 模型验证 | 检查是否符合实际情况 |
| 数据一致性 | 信息是否前后一致 |

## Output Format

### 审阅报告格式

审阅阶段用自然语言总结模型的当前状态和发现的问题：

```markdown
## 模型审阅报告

### 审阅时间
{日期时间}

### 完整性评估
- 业务对象: {数量} 个，{评估结果}
- 关联关系: {数量} 条，{评估结果}
- 处理规则: {数量} 条，{评估结果}
- 状态流转: {数量} 个对象有状态描述，{评估结果}
- 约束条件: {数量} 条，{评估结果}

### 发现的问题
1. **{问题类型}**: {问题描述}
   - 影响: {说明影响}
   - 建议: {改进建议}

2. ...

### 待确认事项
- {事项1}
- {事项2}
...

### 修改历史
- {时间}: {修改内容摘要}
- ...
```

### 模型修改

每次修改后必须**立即写入** `output/business-model.json`（完整 JSON，不要部分更新）。读取当前文件 → 修改对应部分 → 全量写回。同时更新 `output/interview-progress.md` 和 `MEMORY.md`。

## Tips for Execution

1. **主动发现问题**：不要只被动响应用户，要主动检查并提出问题
2. **解释为什么**：当指出问题时，说明为什么这可能是个问题
3. **提供选项**：给出多个解决方案供用户选择，而不是只说"这里有问题"
4. **渐进式完善**：一次聚焦一个问题，避免让用户感到压力
5. **记录决策原因**：每次修改都记录"为什么这样改"，便于后续追溯
6. **保持业务视角**：始终从用户实际工作角度审视模型，不是从技术角度
7. **鼓励质疑**：告诉用户"如果模型哪里不符合你的实际情况，尽管指出"
8. **处理不确定性**：对于不确定的地方，标记为"待确认"，不要强行填充
9. **每次修改后立即静默写入**：调用 `write_file` 全量更新 `output/business-model.json`，同时更新 `interview-progress.md` 和 `MEMORY.md`；对话中只用业务语言确认结果

记住：模型审阅的目标是确保模型成为用户工作方式的准确镜像，任何偏差都应该被纠正。用户的实际工作方式永远是最高标准，即使它看起来"不规范"。
