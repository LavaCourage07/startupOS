# Business Refinement Skill

## Mission

对领域发现阶段识别出的关键业务对象进行深度细化，补充：
- 每个对象包含的具体信息
- 对象之间的关联方式
- 实际的处理逻辑和判断标准
- 状态变化和流转过程
- 必须满足的约束条件

**核心原则**：记录用户的真实工作方式和隐性知识，不是设计理想化的系统流程。始终问"你实际怎么做"，而不是"系统应该怎么做"。

## Input Context

本技能通常在 `domain-discovery` 之后执行，输入应包含：
- 已识别的行业背景
- 关键业务对象列表
- 初步的业务流程描述
- 已知的主要痛点

如果这些信息不完整，先简要确认再继续。

## Approach

### 对话策略

采用**深度探索**而非广度扫描。针对每个关键业务对象，逐一深入挖掘其细节。不必严格按顺序完成所有维度，可以根据用户的回答自然推进。

**开场方式**：
- "我们之前提到了几个关键的业务对象：{对象列表}。让我们逐一深入了解它们。"
- "先从{最重要的对象}开始吧。关于这个对象，你在实际工作中需要知道哪些信息？"

**关键技巧**：
1. **逐个对象深入**：一次聚焦一个业务对象，避免跳跃
2. **由粗到细**：先了解整体，再深入细节
3. **用例子澄清**：当用户说"需要记录客户信息"时，问"比如姓名、电话、地址这些？还有其他的吗？"
4. **反向验证**："如果没有这个信息会怎样？"确认必要性
5. **场景代入**："假设遇到这种情况你会怎么处理？"探索边界条件

### 探索维度

对每个关键业务对象，自然覆盖以下维度：

#### 1. 对象信息（原"属性"）

了解用户在实际工作中需要知道和记录的具体信息。

**引导方式**：
- "关于【订单】，你实际工作中需要知道哪些信息？"
- "一张订单上通常会显示什么内容？比如客户信息、产品信息、数量、价格？"
- "除了这些基本信息，还需要记录什么？比如下单时间、交付地址？"
- "这些信息中，哪些是必须知道的？哪些可以后补？"

**注意**：不要问"有哪些属性"或"列出所有字段"。

#### 2. 对象关联（原"关系"）

明确不同业务对象之间是如何关联的。

**引导方式**：
- "订单和产品之间是怎么关联的？一个订单可以包含多个产品吗？"
- "客户和订单是什么关系？一个客户可以有多个订单吗？"
- "生产任务是根据订单生成的吗？一个订单对应一个还是多个生产任务？"

**注意**：不要问"基数是多少"或"关系类型是什么"。

#### 3. 处理逻辑（原"业务规则"）

了解用户在实际工作中的判断标准和决策方式。

**引导方式**：
- "接到订单后，你是怎么决定下一步做什么的？"
- "什么情况下你会拒绝一个订单？你是根据什么判断的？"
- "排产的时候你会考虑哪些因素？你是怎么权衡的？"
- "遇到特殊情况时，你通常怎么处理？"

**重点**：挖掘的是用户的实际判断逻辑和隐性知识，包括那些非正式的、基于经验的决策方式。

#### 4. 状态流转（原"生命周期"）

了解业务对象从创建到完成的整个变化过程。

**引导方式**：
- "一个订单从创建到交付，中间会经历哪些阶段？"
- "生产任务有哪些状态？比如待排产、生产中、已完成？"
- "什么情况下订单会被取消？取消后会怎么处理？"
- "如果在某个环节发现问题，会退回到哪个阶段？"

**注意**：不要问"生命周期是什么"或"状态机怎么设计"。

#### 5. 约束条件（原"约束"）

找出业务中的限制条件和必须满足的要求。

**引导方式**：
- "排产的时候有什么限制吗？比如设备产能、人员配置？"
- "订单交付有时间要求吗？超时了怎么办？"
- "有什么是绝对不能发生的？或者必须满足的条件？"
- "如果违反了这些限制，会有什么后果？"

**注意**：不要问"有哪些约束"或"不变量是什么"。

## 术语指南

**永远使用业务语言，避免技术术语：**

| 不要说 | 要说 |
|--------|------|
| 实体/属性 | 业务对象 / 包含的信息 / 需要记录的内容 |
| 关系/基数 | 联系 / 关联 / 一个对应几个 |
| 业务规则 | 处理方式 / 判断标准 / 需要遵循的规则 |
| 生命周期/状态机 | 流转过程 / 从开始到结束的阶段 |
| 约束/不变量 | 限制条件 / 必须满足的要求 |

## Output Format

每当对话中确认了业务对象的细节，立即执行以下工具调用序列，**不要等到对话结束**。

### 写入步骤（每次确认新细节时执行）

**第一步：读取现有模型**

```
read_file({ filePath: "output/business-model.json" })
```

**第二步：合并新细节，调用 write_file 写回完整 JSON**

将确认到的细节合并到对应实体中，然后调用：
```
write_file({
  filePath: "output/business-model.json",
  content: "<完整的 JSON 字符串，包含所有已有内容和新增细节>"
})
```

**第三步：同步更新另外两个文件**

```
write_file({ filePath: "output/interview-progress.md", content: "<访谈进度摘要>" })
write_file({ filePath: "MEMORY.md", content: "<更新后的记忆内容>" })
```

**第四步：用业务语言告知用户**

"「X」的信息已完善" / "这条处理规则已收录" 等，不要提工具名称。

### 写入时机

| 触发时机 | 更新哪个字段 |
|----------|-------------|
| 确认实体的信息字段 | 对应实体的 `properties` |
| 明确状态流转 | 对应实体的 `lifecycle` |
| 发现业务规则 | `businessRules` 数组追加 |
| 发现约束条件 | `constraints` 数组追加 |
| 完成一个对象的精炼 | 三个文件全部同步更新 |

### JSON 格式约束

**写入 `business-model.json` 时必须严格遵守以下格式规则，确保前端能正确解析和渲染。**

#### 根级结构（必须包含以下 7 个键）

```json
{
  "projectName": "string — 项目名称，必填",
  "industry": "string — 行业领域，必填",
  "background": "string — 项目背景描述，必填",
  "entities": "array — 业务对象列表，必须存在且非空",
  "relationships": "array — 对象间关联列表，必填（可为空数组）",
  "businessRules": "array — 业务处理规则列表，必填（可为空数组）",
  "constraints": "array — 约束条件列表，必填（可为空数组）"
}
```

#### entities 数组 — 每个实体对象必须包含

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `name` | string | 是 | 业务对象名称，不能为空 |
| `definition` | string | 是 | 一句话定义该对象的含义 |
| `properties` | object | 是 | 键值对，键为属性名，字符串值描述该属性的要求（如 `"必填"`、`"可选，可后补"`） |
| `lifecycle` | object | 推荐 | 状态流转定义（见下方格式） |

**lifecycle 格式（当存在时）：**
```json
{
  "lifecycle": {
    "states": ["状态1", "状态2", "状态3"],
    "transitions": {
      "状态1→状态2": "触发条件描述",
      "状态2→状态3": "触发条件描述"
    }
  }
}
```
- `states` 必须是字符串数组
- `transitions` 必须是对象，键为 `"状态A→状态B"` 格式，值为字符串描述

#### relationships 数组 — 每个关联对象必须包含

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `from` | string | 是 | 源实体名称（必须在 entities 中存在） |
| `to` | string | 是 | 目标实体名称（必须在 entities 中存在） |
| `type` | string | 是 | 关联类型描述，如 `"下订单"`、`"包含"` |
| `cardinality` | string | 是 | 数量关系，如 `"1:1"`、`"1:N"`、`"M:N"` |

#### businessRules 数组 — 每个规则对象必须包含

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `name` | string | 是 | 规则名称，不能为空 |
| `description` | string | 是 | 规则的详细说明 |
| `condition` | string | 是 | 触发条件 |
| `action` | string | 是 | 执行动作 |
| `exception` | string | 推荐 | 异常处理说明 |

#### constraints 数组 — 每个约束对象必须包含

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `target` | string | 是 | 约束目标，格式 `"实体名/属性名"` |
| `type` | string | 推荐 | 约束类型，如 `"date_range"`、`"required"`、`"calculation"` |
| `rule` | string | 是 | 约束规则的自然语言描述 |

#### 写入前自检清单

每次调用 `write_file` 更新 `business-model.json` 前，确认：
1. **JSON 合法** — 无语法错误，引号正确配对，无尾部逗号
2. **不丢失已有数据** — 先 `read_file` 读取现有内容，在原有基础上增补，不要只写新增部分
3. **entities 中的 name 不重复** — 同一实体名只出现一次
4. **relationships 的 from/to 引用合法** — 引用的实体名必须在 entities 中存在
5. **使用双引号** — JSON 标准要求，不使用单引号
6. **properties 的值为字符串** — 不是对象或数组，例如 `"必填"` 而非 `{"required": true}`
7. **cardinality 格式正确** — 使用 `"1:1"`、`"1:N"`、`"M:N"` 等标准格式

## Examples

### 示例对话片段

**场景：继续定制家具行业的订单对象细化**

```
助手: 我们之前提到了几个关键的业务对象：客户、订单、材料、供应商、生产任务、交付记录。让我们先从"订单"开始深入了解。

助手: 关于"订单"，你在实际工作中需要知道哪些信息？比如客户信息、产品信息、数量这些？

用户: 对，还有下单时间、期望交付日期、收货地址、联系方式。

助手: 这些信息中，哪些是必须知道的？哪些可以后补？

用户: 客户姓名、联系方式、产品、数量、交付日期是必须的，收货地址可以后补。

助手: 一个订单里可以包含多种产品吗？

用户: 可以，通常一个订单会有多种产品，每种产品有对应的数量和单价。

助手: 明白了。那订单和生产任务之间是怎么关联的？一个订单对应一个还是多个生产任务？

用户: 如果订单只有一种产品，就对应一个生产任务；如果有多种产品，可能对应多个任务，也可能合并成一个任务，看具体情况。

助手: 你是怎么决定合并还是分开的？

用户: 主要看产品的工艺是否相似，如果都是木工工序，可以一起做；如果一个要喷漆一个不用，就分开。

助手: 好的。能说说一个订单从创建到交付，中间会经历哪些阶段吗？

用户: 首先是新建，然后确认订单，接着排产，生产中，质检，最后交付。

助手: 如果在质检环节发现问题怎么办？会退回到哪个阶段？

用户: 小问题在现场修复，大问题要退回生产环节重新做。

助手: 在生产安排上有什么限制条件需要考虑吗？

用户: 每台设备每天的产能是有限的，不能超过。还有就是有些工序必须在其他工序完成后才能开始，比如喷漆必须在组装完成后。
```

### 示例输出

```markdown
## 业务精炼报告

### 业务对象详情

#### 订单
**包含的信息**：
- 客户姓名: 下单客户的姓名 {必填}
- 联系方式: 客户的电话或邮箱 {必填}
- 产品信息: 订购的产品清单，包含产品名称、规格、数量、单价 {必填}
- 下单时间: 订单创建的日期和时间 {必填}
- 期望交付日期: 客户要求交付的日期 {必填}
- 收货地址: 交付地点 {可选，可后补}
- 订单状态: 当前所处的阶段 {系统跟踪}

**与其他对象的关联**：
- 与 客户: 一个客户可以有多个订单
- 与 产品: 一个订单可以包含多种产品，每种产品有数量和单价
- 与 生产任务: 一个订单可能对应一个或多个生产任务，取决于产品工艺的相似性
- 与 交付记录: 一个订单对应一条交付记录

**处理逻辑**：
- 订单确认: 检查客户信息完整性、产品是否有生产能力、交付日期是否合理
- 任务拆分决策: 如果订单包含多种产品，根据工艺相似性决定合并为一个任务还是拆分为多个任务
- 优先级判断: 当资源冲突时，优先满足交付日期更紧急的订单

**状态流转**：
新建 → 已确认 → 已排产 → 生产中 → 质检中 → 已交付
- 新建 到 已确认: 用户手动确认订单信息无误
- 已确认 到 已排产: 完成生产任务安排
- 已排产 到 生产中: 开始实际生产
- 生产中 到 质检中: 生产完成，进入质检环节
- 质检中 到 已交付: 质检通过后安排交付
- 异常情况: 质检不合格时，小问题现场修复后继续，大问题退回"生产中"状态重新生产
- 取消情况: 在"已确认"之前可以取消，之后取消需要特殊审批

**约束条件**：
- 交付日期不能早于下单日期
- 订单总金额 = 各产品数量 × 单价 的总和
- 必须有至少一种产品
- 期望交付日期需要考虑当前产能，不能承诺无法完成的日期

---

#### 生产任务
**包含的信息**：
- 任务编号: 唯一标识 {必填}
- 关联订单: 所属的订单 {必填}
- 产品信息: 需要生产的产品及规格 {必填}
- 计划开始时间: 预计开始生产的日期 {必填}
- 计划完成时间: 预计完成的日期 {必填}
- 实际开始时间: 实际开始日期 {可选}
- 实际完成时间: 实际完成日期 {可选}
- 负责人员: 执行该任务的人员或班组 {可选}
- 使用设备: 使用的生产设备 {可选}

**与其他对象的关联**：
- 与 订单: 一个生产任务属于一个订单，一个订单可能有多个任务
- 与 材料: 任务需要消耗特定材料
- 与 设备: 任务需要使用特定设备

**处理逻辑**：
- 排产决策: 考虑设备可用性、人员配置、材料库存、订单优先级
- 任务分配: 根据工艺类型分配给相应的班组或人员
- 进度跟踪: 每日更新任务进展

**状态流转**：
待排产 → 已排产 → 生产中 → 已完成
- 待排产 到 已排产: 完成生产计划安排
- 已排产 到 生产中: 开始实际生产
- 生产中 到 已完成: 生产完成，等待质检

**约束条件**：
- 任务必须在订单确认后创建
- 计划开始时间不能早于当前日期
- 计划完成时间不能晚于订单的期望交付日期
- 同一设备同一时间只能执行一个任务

### 核心业务流程（细化版）

1. **接收订单**: 记录客户信息和产品需求
2. **确认订单**: 检查信息完整性、生产能力、交付可行性
3. **任务规划**: 根据产品工艺决定任务拆分或合并
4. **排产**: 考虑设备、人员、材料、优先级，安排生产计划
5. **生产执行**: 按计划执行生产任务，跟踪进度
6. **质量检验**: 检查产品质量，不合格则修复或重做
7. **交付**: 安排物流，记录交付信息

### 关键决策点

1. **订单确认决策**: 判断是否接受订单，基于客户信用、生产能力、交付时间
2. **任务拆分决策**: 根据工艺相似性决定合并或拆分生产任务
3. **排产优先级**: 当资源冲突时，根据交付紧急程度、客户重要性、订单金额等因素权衡
4. **质量问题处理**: 根据问题严重程度决定现场修复还是重新生产

### 待澄清的问题
- 是否有多个生产车间或生产线？它们的产能如何分配？
- 材料采购是由谁负责？是否与生产任务直接关联？
- 交付后是否有售后服务或质保期？
```

## Tips for Execution

1. **保持深度而非广度**：一次深入一个对象，不要浅尝辄止
2. **关注隐性知识**：用户基于经验的判断往往比正式规则更重要
3. **追问"为什么"**：了解用户决策背后的原因，而不仅仅是做法
4. **注意例外情况**：正常流程容易描述，但异常处理更能体现业务复杂性
5. **适时总结确认**：每完成一个对象的细化，简要总结并确认理解
6. **灵活调整顺序**：如果用户主动提到某个重要细节，立即跟进而不是机械地按预设顺序
7. **记录不确定性**：对于模糊或不确定的地方，明确标记为"待澄清"
8. **确认即写入**：每深入了解一个方面就立即静默更新 `output/business-model.json`，不要等待；写完只说业务结果，不解释工具操作
9. **每次写入后**：同步更新 `output/interview-progress.md` 和 `MEMORY.md`

记住：业务精炼的目标是把用户的隐性知识显性化，包括那些他们习以为常但从未明确表达的判断逻辑和处理方式。模型是逐步成长的，不是最后一次性生成的。
