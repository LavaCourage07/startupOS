# V2 样例单元搭建 SOP

本文是从样例单元撰写过程中提取出来的通用经验文件，用于指导后续任何一个完整教材单元的搭建、写作、复审和验收。它不总结某个具体单元的技术内容，而是规定“怎样把一个单元从选题、源码覆盖、章节写作、单元小结到质量闭环完整做出来”。

适用范围：

- 新建一个 Part 内的样例单元。
- 重写已有单元，使其达到正式教材标准。
- 批量写作前建立流程约束。
- 对已经写完的单元做质量复审。

## 1. 样例单元的定义

样例单元不是若干章节文件的集合，而是一段完整的学习路径。它必须让读者从一个可观察的问题出发，逐步掌握相关概念、源码结构、调用链、数据合同、失败边界、测试证据和动手验证方法。

一个合格样例单元至少包含四层产物：

| 层级 | 产物 | 作用 |
| --- | --- | --- |
| 单元导读 | 单元总问题、主线案例、范围边界、源码覆盖台账 | 让读者知道本单元为什么存在、要解决什么、不解决什么 |
| 正式章节 | 若干连续课程正文 | 逐步讲清每个关键问题、源码窗口和验证方式 |
| 单元小结 | 整体认知框架、排查地图、综合实验、口头验收 | 帮读者把分散知识重新组织成系统能力 |
| 写作台账 | 源码覆盖、测试覆盖、质量复审记录 | 防止遗漏、误判和过度承诺 |

只有这四层都成立，才能称为“完整单元”。仅有章节数量、文件列表或目录结构，都不能称为完整单元。

## 2. 搭建样例单元时最容易踩的坑

### 2.1 把进度当质量

常见表现：

- 文件创建完，就认为单元完成。
- 章节编号排齐，就认为课程体系完整。
- 前几章写得详细，后几章变成压缩讲义。
- 用大段目录、清单、结论替代真实教学。

根因：

- 缺少单元级完成标准。
- 写作目标停留在“覆盖章节”，没有落到“教会读者”。
- 没有逐章质量闸门，导致越写越薄。

规则：

1. 文件存在只表示进入草稿。
2. 章节数量不能证明教学质量。
3. 每一章都必须独立通过质量闸门，不能靠前后章节互相补洞。
4. 任何章节明显短、浅、缺少源码或缺少验证，都必须退回重写。

### 2.2 主题先行导致源码遗漏

常见表现：

- 先按想讲的概念写章节，再临时找源码支持。
- 讲了一个目录里的主文件，却漏掉同目录的辅助文件、导出文件、转换文件或测试文件。
- 大文件被引用一次后，就误以为整个文件都已讲完。
- 单元结束后才发现某些直接相关文件没有进入正文。

根因：

- 没有在开写前建立源码覆盖台账。
- 没有区分“背景引用”和“直接精读”。
- 没有把生产源码与测试文件配对。

规则：

1. 开写前必须先做源码盘点，再写正文。
2. 每个文件必须有状态：本单元精读、后续单元精读、仅背景引用、不纳入教材。
3. 直接精读必须写明代码窗口、讲解责任和验证入口。
4. 同目录、同概念、同调用链都不能自动代表源码已覆盖。
5. 大文件必须按代码窗口登记，不得按文件名一次性算完。

### 2.3 正文混入写作过程

常见表现：

- 课程正文出现作者给自己的提示。
- 正文里出现协作过程、修改过程、交付说明、自我解释。
- 用“为了满足要求”“接下来应该”“先建立”这类写作语言替代正式教学语言。

根因：

- 没有区分“作者工作台”和“正式教材正文”。
- 写作时把内部计划直接带入面向读者的文本。
- 文风检查缺失。

规则：

1. `textbook/` 下的正式章节只面向学习者。
2. 正文只讲技术事实、概念、源码、推理、练习和验收。
3. 写作计划、复盘、SOP、进度说明只能放在管理文件中。
4. 图解前可以写“本图回答的问题是……”，不能写作者侧操作提示。
5. 任何自我辩解、协作痕迹、提示词痕迹都必须删除。

### 2.4 主线案例不稳定

常见表现：

- 每章换一个例子，读者无法形成连续理解。
- 案例只在开头出现，后文又回到抽象术语堆叠。
- 案例太贴近“教程写作”本身，导致读者混淆学习场景和产品运行场景。
- 案例无法覆盖失败路径，只能解释正常流程。

根因：

- 没有先设计单元级学习主线。
- 案例没有真实动作、数据变化和边界变化。
- 章节之间缺少“上一章留下的问题”和“下一章要解决的问题”。

规则：

1. 一个单元必须有一条连续、可观察、可推进的真实案例。
2. 案例必须能跨过本单元的关键技术边界。
3. 每章都要让同一案例进入一个新的问题，而不是重新开场。
4. 案例必须能承载错误、异常、误解和测试场景。
5. 如果案例不适合，应尽早替换，不要为了保留旧稿牺牲清晰度。

### 2.5 概念解释不够分层

常见表现：

- 直接抛术语，零基础读者无法跟上。
- 用一句类比替代准确边界。
- 只解释“是什么”，不解释“为什么这样设计”和“不能代表什么”。
- 相近概念没有对比，读者记住名称却不会排错。

根因：

- 写作顺序从源码名词开始，而不是从读者可观察现象开始。
- 缺少“直觉、术语、边界、反例”的概念阶梯。

规则：

1. 每个关键概念都要先从现象进入。
2. 先给通俗直觉，再给准确术语。
3. 必须写清楚它负责什么、不负责什么。
4. 相近概念必须做对照表或对照段落。
5. 概念解释最终必须回到源码字段、函数或调用边界。

### 2.6 测试证据说过头

常见表现：

- 一个单元测试通过，就写成整个链路可靠。
- 源码存在某个分支，就写成行为已经被测试固定。
- 没有找到测试时，正文跳过测试缺口。
- 测试命令没有实际跑通，却写成“已验证”。

根因：

- 没有区分源码事实、测试证据和推断。
- 没有逐个测试回答 Given/When/Then。
- 没有把“尚未覆盖”作为必须写出的教学内容。

规则：

1. 测试只能证明它实际断言过的内容。
2. 每个测试说明必须回答：准备了什么、触发了什么、断言了什么。
3. 测试没有跨过的边界，正文不得替它承诺。
4. 没找到测试时必须写明缺口和应补测试。
5. 测试命令未成功执行时，不能写“已通过”。

### 2.7 图解没有承担推理任务

常见表现：

- 图只是把标题换成节点，没有解释新的关系。
- 图前没有说明要回答的问题。
- 图后没有逐节点、逐箭头解释。
- 图中关系比源码更笼统，甚至误导读者。

根因：

- 把图当装饰，而不是技术推理工具。
- 没有把图中的每个节点绑定到源码对象或数据责任。

规则：

1. 一张图只回答一个问题。
2. 图前必须说明读者应带着什么问题看图。
3. 图后必须解释节点、箭头、数据、停止边界。
4. 图中对象必须能在源码、类型、请求、状态或测试中找到对应物。
5. 图不能替代源码精读，只能帮助读者进入源码。

### 2.8 Markdown 结构质量不稳定

常见表现：

- 表格列数不一致。
- 表头与列内容不匹配。
- 链接无法点击、路径不存在、行号不对应论点。
- 长章节多次修改后出现重复标题、跳级标题或残留旧表述。

根因：

- 没有把 Markdown 结构当作工程质量检查项。
- 写作后缺少机械检查和人工复读。

规则：

1. 每次编辑后检查表格列数。
2. 表头必须准确，不允许沿用旧表头。
3. 本地 Markdown 链接前后保留空格。
4. 源码链接必须指向真实文件和有效代码窗口。
5. 结构检查只能发现格式问题，不能替代内容复审。

### 2.9 单元小结写成“浓缩目录”

常见表现：

- 小结只是把本单元章节标题重新列一遍。
- 开头很快进入大表格、大图或源码台账，读者还没建立抓手。
- 认知图、源码台账、测试证据都在，但阅读顺序不友好。
- 文字信息密度过高，读者能查到内容，却不容易形成整体理解。
- 配图只是装饰，没有帮助读者跨过关键认知转折。

根因：

- 把单元小结当成“信息归档”，而不是“复盘课”。
- 先追求完整覆盖，再考虑阅读路径，导致读者一开始就被细节压住。
- 缺少面向零基础读者的分层入口：一句话总判断、阅读路线、核心对象、源码查证、练习验收。

规则：

1. 单元小结首先是一堂复盘课，其次才是目录和台账。
2. 开头必须先给读者一个低负担入口，例如一句核心判断、三条关键含义和本页阅读路径。
3. 复杂表格和源码台账应放在读者已经建立框架之后，不能一上来压给读者。
4. 长表格应尽量拆成小块认知卡片；每张表前必须说明读者要用它解决什么问题。
5. 配图必须放在认知转折处，帮助读者理解结构、误区或排查路径，不能平均铺图。
6. 小结结尾必须把本单元压缩成一句可复用的判断原则，并说明它如何进入下一单元。

## 3. 标准搭建流程

### 3.1 第一步：确定单元能力目标

开写前先回答五个问题：

1. 读者学完这个单元后，能独立解决什么类型的问题？
2. 这个单元的主线案例是什么？
3. 主线案例会经过哪些系统边界？
4. 本单元明确不讲哪些相邻问题？
5. 本单元最终如何验收读者真的理解了？

如果不能回答这五个问题，说明单元还没有准备好。

### 3.2 第二步：建立源码覆盖台账

源码覆盖台账必须先于正文存在。建议字段如下：

| 字段 | 说明 |
| --- | --- |
| 文件路径 | 真实仓库路径 |
| 文件类型 | 生产源码、测试、配置、文档、脚本、静态资源 |
| 本单元状态 | 精读、背景引用、后续单元、暂不纳入 |
| 主讲章节 | 哪一章负责直接讲解 |
| 代码窗口 | 关键行段或函数名 |
| 教学责任 | 本文件在本单元解决什么问题 |
| 配对验证 | 对应测试、命令、人工检查或测试缺口 |
| 备注 | 保留原因、风险、与后续单元的关系 |

台账不是附录装饰，而是防止遗漏的主控表。正文写完后必须反向核对台账。

### 3.3 第三步：设计章节因果链

章节顺序应来自问题推进，而不是文件排序。

推荐结构：

1. 第一章建立最容易误解的入口边界。
2. 中间章节逐步引入配置、状态、数据、转换、持久化、恢复、测试等新问题。
3. 最后一章做综合工作坊或实验，把前面概念转成可操作验证。
4. 单元小结重新组织整体框架，而不是重复目录。

每一章都要能回答：

- 本章接住了上一章哪个未解决问题？
- 本章新引入了哪个系统对象？
- 本章在哪个边界停止？
- 下一章为什么自然出现？

### 3.4 第四步：逐章写作

每章必须完成以下教学动作：

1. 用主线案例提出本章具体问题。
2. 用初学者能理解的语言建立直觉。
3. 区分相近概念，写清各自责任。
4. 用图解呈现关键关系，并解释图中每个节点和箭头。
5. 从真实源码入口进入，逐段解释输入、状态、分支、输出。
6. 写明调用者、被调用者和数据如何移动。
7. 给出关键类型或数据示例。
8. 讲失败路径、边界条件和常见误判。
9. 写测试证据和测试缺口。
10. 设置小实验与口头验收。
11. 用章节小结收束，并自然引向下一章。

章节标题可以灵活，但这些教学动作不能省略。

### 3.5 第五步：编写单元小结

单元小结不是章节摘要，也不是源码台账的集中展示。它应当写成一堂可独立阅读的复盘课：读者即使暂时忘记了前面每节课的细节，也能通过小结重新建立本单元的整体地图。

单元小结的第一目标是可读、易读、便于理解、清晰。完整性仍然重要，但完整性不能压倒阅读顺序。合格的小结应先给读者抓手，再给结构，再给源码和证据。

推荐顺序：

1. 用一个真实场景重新唤起本单元总问题。
2. 给出一句核心判断，让读者先知道本单元最重要的结论。
3. 把核心判断拆成三到五条容易记住的含义。
4. 给出本页阅读路径，说明先读什么、后读什么、每段解决什么问题。
5. 用一张总体认知图解释主对象和主路径，并在图后分段讲解。
6. 把最容易混淆的概念拆成小块认知卡片或短表格，而不是堆成长表。
7. 再放章节因果链，让读者知道每节课补上了哪一段判断能力。
8. 在读者已有框架后放源码覆盖台账，说明已精读、已验证和未覆盖边界。
9. 用排查地图、纸面实验或综合练习把知识转成可操作能力。
10. 用测试证据表说明哪些结论被证明，哪些仍不能承诺。
11. 用口头验收和一句收束原则结束，并自然连接下一单元。

配图要求：

1. 单元小结需要优先在认知转折处配图，例如总体结构、关键误区、排查路径。
2. 配图必须帮助理解，不为装饰而出现。
3. 小黑配图应让小黑承担核心动作，例如分拣对象、阻止混用、逐层排查。
4. 一篇小结通常 2-8 张配图即可；不要把小结做成画册。
5. 配图前后的文字必须说明它解决的理解问题，但不要写成作者提示。

合格单元小结应包含：

1. 单元总问题。
2. 一句核心判断。
3. 清晰阅读路径。
4. 主线案例的完整变化过程。
5. 一张总体认知图及图后解释。
6. 三到五个核心区分。
7. 章节因果链。
8. 源码覆盖台账。
9. 相邻但未讲文件的边界说明。
10. 排查地图或判断流程。
11. 综合实验。
12. 测试证据范围与缺口。
13. 进入下一单元前的口头验收。

不合格信号：

1. 读者看完开头仍不知道本单元要解决什么。
2. 大表格或源码台账出现得太早，阻断理解。
3. 小结只是“每节课分别讲了什么”，没有重建整体结构。
4. 每个部分都完整，但读者不知道应该按什么顺序阅读。
5. 图和配图没有降低理解难度。
6. 读者看完小结仍无法用自己的话说出本单元的整体框架。

出现以上任一情况，小结需要重写结构，而不是只补几句说明。

### 3.6 第六步：复审与返工

复审必须把“内容质量”和“结构质量”分开看。

内容复审：

1. 是否真正面向零基础读者解释。
2. 是否有足够深度，而不是只有结论。
3. 是否每个核心概念都有边界和反例。
4. 是否每个源码判断都可回到真实文件。
5. 是否每个测试结论都没有越界。

结构复审：

1. 标题是否清晰。
2. 表格是否有效。
3. 链接是否真实可点。
4. 代码窗口是否对应论点。
5. 是否残留作者提示或协作语言。
6. 是否有重复、断裂、跳跃和旧稿痕迹。

发现问题后不要只修表面句子。若问题来自章节结构，应整节重写；若问题来自单元边界，应先更新台账和章节因果链，再改正文。

## 4. 单章质量闸门

任何章节进入样章级别前，必须通过下表：

| 闸门 | 合格标准 | 不合格表现 |
| --- | --- | --- |
| 问题明确 | 本章只解决一个清晰主问题 | 只是介绍一个文件或概念 |
| 案例连续 | 主线案例在关键解释中持续出现 | 案例只在开头出现一次 |
| 概念分层 | 先直觉，后术语，再边界 | 直接堆术语 |
| 图解有效 | 图承担具体推理任务 | 图只是装饰性流程图 |
| 源码精读 | 真实代码窗口被逐段解释 | 只有文件链接或结论 |
| 调用链清楚 | 能说清调用者、被调用者、数据流 | 只说“调用了某函数” |
| 类型具体 | 字段含义和责任边界明确 | 泛泛说“类型是合同” |
| 失败路径 | 写出异常、误判或边界条件 | 只有正常路径 |
| 测试克制 | 证据范围与缺口都写明 | 把局部测试说成全链路可靠 |
| 练习可验收 | 有定位、推演、微改动或复述标准 | 只有开放式思考题 |
| 文风正式 | 面向学习者，无作者提示 | 出现写作过程或协作痕迹 |

任一闸门不通过，章节仍是草稿。

## 5. 单元质量闸门

完整单元必须通过下表：

| 闸门 | 合格标准 | 不合格表现 |
| --- | --- | --- |
| 单元目标 | 学完后能力可描述、可验收 | 只有主题名称 |
| 范围边界 | 本单元讲什么、不讲什么都明确 | 相邻链路混在一起 |
| 源码覆盖 | 台账与正文互相对应 | 写完后才发现漏文件 |
| 章节递进 | 每章接住前一章并引出后一章 | 章节互相独立 |
| 深度稳定 | 后续章节不低于前面章节标准 | 越写越短、越写越薄 |
| 小结成框架 | 小结有低负担入口、阅读路径、认知图、核心区分、源码台账、排查练习和口头验收 | 小结只是目录复述，或一开始就用大表格压住读者 |
| 证据克制 | 测试、源码、推断边界清楚 | 承诺超过证据 |
| 正文洁净 | 正式课程没有作者侧语言 | 正文残留过程说明 |
| 可继续扩展 | 后续单元的衔接问题明确 | 不知道下一组该讲什么 |

单元验收不是一次性动作。每次补源码、补章节、补测试说明后，都要重新跑一次台账和质量闸门。

## 6. 建议执行检查

以下检查只能辅助发现问题，不能替代人工复审。

检查 Markdown 空白问题：

```bash
git diff --check -- learning-note/full-project-course-v2
```

检查可能混入正文的作者侧语言：

```bash
rg -n "为了满足要求|我会|我将|接下来我|先建立|不要先|直接开写|交付|正文是面向|提示词" learning-note/full-project-course-v2/textbook
```

检查源码链接和行号引用：

```bash
rg -n "\\]\\(|#L[0-9]+" learning-note/full-project-course-v2/textbook
```

检查待办、占位和未完成标记：

```bash
rg -n "TODO|FIXME|待补|待定|占位|以后再写" learning-note/full-project-course-v2
```

检查表格列数时，应使用脚本或 `awk` 对表头行与分隔行做一致性检查。发现表格错误后，必须同时检查表头语义是否仍然准确。

## 7. 返工原则

返工不是把章节加长，而是恢复教学责任。

遇到以下情况，应直接重写相关部分：

1. 章节没有清晰问题。
2. 案例不能支撑源码讲解。
3. 源码只是被引用，没有被解释。
4. 概念之间边界不清。
5. 测试证据被夸大。
6. 正文出现作者提示或协作痕迹。
7. 单元小结不能形成整体框架，或虽然信息完整但阅读负担过高。

遇到以下情况，应先更新台账，再改正文：

1. 发现遗漏源码。
2. 发现同一大文件承担多个不同职责。
3. 发现测试文件没有配对生产文件。
4. 发现某个主题实际属于后续单元。

遇到以下情况，应先停下复查源码，而不是继续扩写：

1. 调用链不确定。
2. 字段含义不确定。
3. 测试是否覆盖不确定。
4. 文件是否仍被跟踪不确定。
5. 某个行为只是推断，没有源码证据。

## 8. 硬规则清单

1. 正式教材正文面向学习者，不写作者提示和协作过程。
2. 第一原则是全面且有深度，不能遗漏。
3. 样例单元的目标是教会读者，不是凑齐章节。
4. 开写前必须先建立源码覆盖台账。
5. 每个源码文件都要有明确状态和教学责任。
6. 大文件按代码窗口讲，不按文件名一次性算完。
7. 每章必须包含概念、图解、源码、边界、测试和验收。
8. 测试证据只证明它实际断言过的内容。
9. 没有测试时必须写缺口。
10. 单元小结必须先保证可读、易读、清晰，再承载源码台账和验收。
11. Markdown 表格、链接、行号必须检查。
12. 一旦发现章节变薄、源码遗漏或证据越界，必须返工，不得继续堆后续章节。
