# L06：Skill 定义的常见误读和失败边界

前五课分别读了 Skill 定义、Project Interview 模板、最小 Skill、状态文件和报告文件。本课把这些材料合在一起，专门处理失败边界。学习 Part L 时，很多错误不是代码不会运行，而是读者把文件类型看错了。

本课的问题是：当 Skill、模板、状态、报告和工作目录混在一起时，怎样从症状反推责任边界？

## 1. 五种常见误读

| 误读 | 表现 | 正确边界 |
| --- | --- | --- |
| 把入口当能力 | 看到首页卡片或 Skill 名称，就以为能力已经完整存在。 | 入口只发起动作，能力定义要看 `SKILL.md`。 |
| 把定义当执行 | 看到正文写“创建文件”，就以为文件已经生成。 | 定义说明期望行为，执行结果要看运行记录或产物。 |
| 把模板当产物 | 修改 `templates/skills/**` 以为是在改用户结果。 | 模板是源材料，用户产物应落在工作目录。 |
| 把报告当源码 | 看到 `PASS` 就认为当前实现一定正确。 | 报告只证明特定时间和范围内的检查结论。 |
| 把工具说明当工具实现 | 看到 `allowedTools` 就认为工具已注册。 | 工具实现和注册要回到运行时源码验证。 |

这些误读都会让排查方向偏离真实边界。

## 2. 症状一：产物写到了模板目录

假设小林使用一个 Skill 生成旅行计划，结果文件出现在 `templates/skills/travel-planner/`。这通常不是“生成成功”，而是目录边界错误。

`templates/skills/**` 的角色是源定义或模板材料。根据 L01 的区分，`SKILL.md` 描述能力，模板文件提供初始结构，状态文件可以作为样例。用户任务产生的旅行计划、预算表、路线草案，应写到工作目录或明确的输出目录。

排查顺序应是：

1. 检查 `SKILL.md` 是否声明了类似 `outputDir` 的字段。
2. 检查正文是否使用 `${OUTPUT_DIR}`、`skills/{skill-id}` 或硬编码路径。
3. 检查调用方是否真正替换了变量。
4. 检查文件工具的工作目录解析规则。
5. 检查是否把模板目录当成当前 CWD。

## 3. 症状二：用户第一次访谈被当成读文件失败

[templates/skills/domain-discovery/SKILL.md 第 87 行](../../../../templates/skills/domain-discovery/SKILL.md#L87) 明确要求先 `list_files` 检查 `output` 目录，只有存在 `business-model.json` 时才读取；不存在时使用初始结构。这说明“文件不存在”在 Phase 1 是正常状态。

如果实现或执行者一开始就调用 `read_file`，然后把缺失文件当错误反馈给用户，就是没有遵守 Skill 的失败边界。正确行为是初始化一个空业务模型，再把小林的旅行项目名称、预算、人数、偏好逐步写进去。

## 4. 症状三：工具声明和实际工具不一致

[templates/project-interview/Tool.md 第 3 行](../../../../templates/project-interview/Tool.md#L3) 列出 `allowedTools`，正文又逐个解释工具用途。但这份文件是模板层说明，不是工具注册表。

如果运行时没有注册 `write_file`，即使 `Tool.md` 写了它，Agent 仍然不能真正写文件。反过来，如果运行时注册了危险工具，但 `Tool.md` 没有限制和说明，模型可能误用或用户无法理解风险。

因此，排查工具问题必须同时看两边：

| 材料 | 回答的问题 |
| --- | --- |
| `Tool.md` | 模板希望 Agent 如何理解和使用工具。 |
| 运行时工具注册 | 系统实际提供了哪些可执行工具。 |
| 工具测试 | 哪些参数、路径和失败分支已经被断言。 |

Part L 只讲第一列。后两列属于 Part E/F 的运行时证据。

## 5. 症状四：报告 PASS 被当成当前保证

[skills/reports/architecture-guard/architecture-guard-20260729-120736.md 第 14 行](../../../../skills/reports/architecture-guard/architecture-guard-20260729-120736.md#L14) 的 `PASS` 只在报告范围内成立。报告自己在 [skills/reports/architecture-guard/architecture-guard-20260729-120736.md 第 64 行](../../../../skills/reports/architecture-guard/architecture-guard-20260729-120736.md#L64) 列出未执行的真实 package artifact smoke 等残余风险。

如果教材或工程说明只保留 PASS，删除残余风险，就是把报告变成了宣传语。正确做法是同时记录结论和未证明部分。

## 6. 症状五：模板残留被忽略

[templates/project-interview/Tool.md 第 154 行](../../../../templates/project-interview/Tool.md#L154) 出现孤立字符 `l`。它不一定导致运行失败，但它是模板质量信号。正式教材不能把这种细节当作不存在。

正确表述是：当前文件末尾存在疑似残留字符；本课不修改源码，只把它登记为模板质量风险。若后续清理，应通过单独变更删除，并检查是否有测试或文档受影响。

## 7. 测试证据与缺口

本课是失败边界课，证据来自前几课已精读的模板和报告：`domain-discovery` 证明新项目缺少 `business-model.json` 可被视为正常初始化状态，`Tool.md` 证明模板声明了工具清单，architecture guard report 证明一次检查必须带范围和残余风险。

这些证据仍停留在阅读和推理层。目录错位、工具注册不一致、报告过期等问题要变成自动化测试，需要分别进入运行时路径解析测试、工具注册测试和检查命令复跑。本课不把这些推理写成已验证生产行为。

## 8. 小实验与口头验收

给出四个现象，请写出第一排查文件：

1. Skill 能打开，但生成文件出现在模板目录。
2. 全新访谈项目一开始提示 `business-model.json` 读取失败。
3. `Tool.md` 写了 `write_file`，但实际回复说无法写文件。
4. 文档写“架构已通过检查”，但用户问当前代码是否仍然通过。

口头验收：

1. 为什么 `SKILL.md` 不是执行结果？
2. 为什么模板目录不是用户产物目录？
3. 为什么文件不存在有时是正常状态？
4. 为什么工具说明不等于工具实现？
5. 为什么报告必须连同残余风险一起引用？

合上本课后，应能从症状回到边界，而不是只按文件名猜原因。下一课是第一小单元工作坊，会把所有文件重新组织成一张排查地图。
