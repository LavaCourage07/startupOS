# M24 测试目录结构如何阅读——从 `tests/` 到测试金字塔

小林想了解 OriginOS 的测试是如何组织的。她打开 `tests/` 目录，看到 `e2e/`、`integration/`、`mocks/` 三个子目录。她以为测试很简单——就三类。

但她不知道的是：**每个测试目录对应不同的测试层级，覆盖不同的测试范围，使用不同的测试工具**。更关键的是，测试目录的组织方式直接反映了"测试金字塔"的理念。

本课解决一个理解问题：当你面对 OriginOS 的测试目录时，怎样理解每个目录的作用、它们之间的层级关系、以及测试覆盖的范围。

## 场景：从"三个目录"到"测试金字塔"

### 1.1 `tests/` 目录的顶层结构

OriginOS 的测试目录位于 `tests/`：

```
tests/
├── e2e/                    # 端到端测试
│   └── epic-2-workspace.spec.ts
├── integration/            # 集成测试
│   └── epic-2-workspace-api.test.ts
├── mocks/                  # 模拟数据
│   └── ...
└── setup.ts                # 测试环境配置
```

### 1.2 测试金字塔

OriginOS 的测试组织遵循"测试金字塔"理念：

```
    ▲
   /  \
  / E2E \          # 端到端测试（少而精）
 /--------\
/ Integration \   # 集成测试（中等数量）
--------------
    Unit        # 单元测试（大量）
```

| 测试层级 | 目录 | 数量 | 执行速度 | 维护成本 |
| --- | --- | --- | --- | --- |
| 单元测试 | 各包内的 `*.test.ts` | 大量 | 快 | 低 |
| 集成测试 | `tests/integration/` | 中等 | 中等 | 中等 |
| E2E 测试 | `tests/e2e/` | 少量 | 慢 | 高 |

**关键理解**：测试金字塔的核心思想是——底层测试（单元测试）数量多、执行快、成本低；顶层测试（E2E 测试）数量少、执行慢、成本高。

## 2. 各测试层级精读

### 2.1 单元测试

单元测试位于各包内，与源代码放在一起：

```
packages/pi-tasks/test/
├── evidence-gate.test.js
├── versioned-ledger.test.js
└── upstream-baseline.test.js
```

**特点**：

| 特征 | 说明 |
| --- | --- |
| 位置 | 与源代码在同一个包内 |
| 命名 | `*.test.js` 或 `*.test.ts` |
| 范围 | 单个函数或组件 |
| 依赖 | 尽可能少的外部依赖 |
| 执行速度 | 快（毫秒级） |

### 2.2 集成测试

集成测试位于 `tests/integration/`：

```
tests/integration/
└── epic-2-workspace-api.test.ts
```

**特点**：

| 特征 | 说明 |
| --- | --- |
| 位置 | `tests/integration/` |
| 命名 | `*.test.ts` |
| 范围 | 多个模块的交互 |
| 依赖 | 需要真实或模拟的外部服务 |
| 执行速度 | 中等（秒级） |

### 2.3 E2E 测试

E2E 测试位于 `tests/e2e/`：

```
tests/e2e/
└── epic-2-workspace.spec.ts
```

**特点**：

| 特征 | 说明 |
| --- | --- |
| 位置 | `tests/e2e/` |
| 命名 | `*.spec.ts` |
| 范围 | 完整的用户场景 |
| 依赖 | 需要完整的应用环境 |
| 执行速度 | 慢（分钟级） |

## 3. 测试目录的阅读方法

### 3.1 三步阅读法

**第一步：看测试层级**

测试属于哪个层级？单元、集成还是 E2E？

**第二步：看测试范围**

测试覆盖了什么？单个函数、模块交互还是完整场景？

**第三步：看测试工具**

测试使用了什么工具？Vitest、Testing Library、Playwright？

### 3.2 测试工具链

| 测试层级 | 测试框架 | 断言库 | 模拟工具 |
| --- | --- | --- | --- |
| 单元测试 | Vitest | Vitest 内置 | Vitest mock |
| 集成测试 | Vitest | Vitest 内置 | MSW（Mock Service Worker） |
| E2E 测试 | Playwright | Playwright 内置 | — |

## 5. 练习：测试层级判断

### 任务 A：判断测试层级

已知信息：有一个测试文件测试了"用户登录后创建工作空间"的完整流程。

问题：这属于哪个测试层级？为什么？

### 任务 B：选择测试工具

已知信息：需要测试一个 API 接口的响应。

问题：应该使用什么测试工具和框架？

### 参考答案

**任务 A：**

| 层级 | 适用性 | 原因 |
| --- | --- | --- |
| E2E | ✅ 适合 | 测试了完整的用户场景 |
| 集成 | ❌ 不适合 | 范围太大，不是模块间的交互 |
| 单元 | ❌ 不适合 | 范围太大，不是单个函数 |

**任务 B：**

| 工具 | 适用性 | 原因 |
| --- | --- | --- |
| Vitest + MSW | ✅ 适合 | 适合 API 接口测试 |
| Playwright | ❌ 不适合 | 适合 UI 测试，不适合 API 测试 |

## 6. 口头验收

学完本课后，不看正文也应能回答下面五个问题：

1. `tests/` 目录下有哪些子目录？它们分别对应什么测试层级？
2. 测试金字塔的理念是什么？各层级的特点是什么？
3. 单元测试、集成测试、E2E 测试的区别是什么？
4. 各测试层级使用了什么工具？
5. 当你需要添加新的测试时，应该如何选择测试层级和工具？

合格回答不要求背诵每个测试文件的具体内容，但必须能说清测试目录的组织方式、测试金字塔的理念、以及测试工具的选择。能说清"测试覆盖了什么"比只说清"测试在哪里"更重要。
