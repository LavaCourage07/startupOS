# M16 数据迁移策略如何阅读——从 Web 到 Desktop 的数据迁移

小林在 Web 版本上创建了一个 Agent，积累了大量记忆和知识。现在她想把这个 Agent 迁移到 Desktop 版本。她打开 `packages/web/data/` 和 `packages/desktop/data/`，发现两者的目录结构完全相同。

但她不知道的是：**目录结构相同只是迁移的前提，真正的迁移还需要考虑数据一致性、版本兼容性、以及迁移后的验证**。

本课解决一个理解问题：当你面对 OriginOS 的数据迁移需求时，怎样理解迁移策略、评估迁移风险、以及执行迁移后的验证。

## 场景：从"目录结构相同"到"迁移安全完成"

### 1.1 数据迁移的需求来源

OriginOS 的数据迁移需求主要来自以下场景：

| 场景 | 描述 | 迁移方向 |
| --- | --- | --- |
| Web → Desktop | 用户在 Web 版本上工作，想在 Desktop 版本上继续 | Web → Desktop |
| Desktop → Web | 用户在 Desktop 版本上工作，想在 Web 版本上继续 | Desktop → Web |
| 版本升级 | 新版本的数据格式与旧版本不兼容 | 旧版本 → 新版本 |
| 备份恢复 | 数据丢失后从备份恢复 | 备份 → 当前 |

### 1.2 迁移的前提条件

数据迁移的前提条件：

| 条件 | 说明 | 验证方法 |
| --- | --- | --- |
| 目录结构相同 | Web 和 Desktop 的数据目录结构一致 | 对比 `packages/web/data/` 和 `packages/desktop/data/` |
| 文件格式兼容 | 数据文件的格式在两个版本中都能解析 | 检查 JSON/JSONL/Markdown 的版本兼容性 |
| 版本一致 | 两个版本的应用版本号相同或兼容 | 检查 `package.json` 中的版本号 |
| 无冲突 | 目标目录中没有同名 Agent 或项目 | 检查目标目录下的 `agents/` 和 `projects/` |

## 2. 迁移策略

### 2.1 全量迁移 vs 增量迁移

| 策略 | 描述 | 适用场景 | 风险 |
| --- | --- | --- | --- |
| 全量迁移 | 复制整个 `data/` 目录 | 首次迁移、数据量小 | 覆盖目标目录的现有数据 |
| 增量迁移 | 只迁移新增或修改的数据 | 多次迁移、数据量大 | 需要追踪数据变更 |
| 选择性迁移 | 只迁移特定的 Agent 或项目 | 只需要迁移部分数据 | 可能遗漏依赖数据 |

### 2.2 迁移步骤

**全量迁移的步骤**：

1. **备份目标目录**：在迁移前备份 `packages/desktop/data/`
2. **停止应用**：确保 Desktop 版本没有在运行
3. **复制数据**：将 `packages/web/data/` 复制到 `packages/desktop/data/`
4. **验证数据**：检查复制后的数据完整性
5. **启动应用**：启动 Desktop 版本，验证功能正常

**增量迁移的步骤**：

1. **对比差异**：比较源目录和目标目录的文件差异
2. **识别新增/修改**：找出新增或修改的文件
3. **复制变更**：只复制新增或修改的文件
4. **验证数据**：检查迁移后的数据完整性

## 3. 迁移风险与应对

### 3.1 常见迁移风险

| 风险 | 描述 | 应对措施 |
| --- | --- | --- |
| 数据覆盖 | 目标目录已有同名 Agent/项目 | 重命名或合并 |
| 版本不兼容 | 数据格式在新版本中无法解析 | 升级应用版本或转换数据格式 |
| 数据损坏 | 迁移过程中文件损坏 | 使用校验和验证文件完整性 |
| 路径依赖 | 数据中包含绝对路径 | 使用相对路径或路径映射 |

### 3.2 数据一致性验证

迁移后需要验证数据一致性：

| 验证项 | 方法 | 通过标准 |
| --- | --- | --- |
| 文件数量 | 对比源目录和目标目录的文件数量 | 相同 |
| 文件大小 | 对比关键文件的大小 | 相同 |
| 校验和 | 计算 SHA256 校验和 | 相同 |
| 应用启动 | 启动应用，检查功能正常 | 无报错 |

## 5. 练习：迁移策略选择

### 任务 A：选择迁移策略

已知信息：用户想在 Web 和 Desktop 版本之间同步 Agent 数据，数据量较小（< 100MB）。

问题：应该选择全量迁移还是增量迁移？为什么？

### 任务 B：评估迁移风险

已知信息：目标目录中已有一个同名 Agent。

问题：应该如何处理？有哪些风险？

### 参考答案

**任务 A：**

| 策略 | 适用性 | 原因 |
| --- | --- | --- |
| 全量迁移 | ✅ 适合 | 数据量小，操作简单，不易出错 |
| 增量迁移 | ❌ 不适合 | 数据量小，增量迁移的复杂度不值得 |

**任务 B：**

| 处理方法 | 风险 |
| --- | --- |
| 覆盖 | 丢失目标目录中的 Agent 数据 |
| 重命名 | 需要更新所有引用该 Agent 的配置 |
| 合并 | 复杂度高，需要处理冲突 |

## 6. 口头验收

学完本课后，不看正文也应能回答下面五个问题：

1. 数据迁移的前提条件是什么？
2. 全量迁移和增量迁移的区别是什么？各有什么优缺点？
3. 数据迁移有哪些常见风险？如何应对？
4. 迁移后应该如何验证数据一致性？
5. 当你需要迁移数据时，应该按什么步骤操作？

合格回答不要求背诵每个步骤的具体命令，但必须能说清迁移策略、风险评估、以及验证方法。能说清"如何安全迁移"比只说清"迁移是什么"更重要。
