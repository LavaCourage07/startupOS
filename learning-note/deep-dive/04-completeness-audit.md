# 04 深度课程完整性审计

本文件回答一个关键问题：

> 现在这套深入课程计划，能不能让人完全学会 OriginOS？

结论先说：

> 旧的 24 节主线课不够。新的深入版必须按 72 节源码课 + 4 个综合实战推进，并用文件覆盖矩阵约束每章内容。

## 1. 为什么旧计划不够

旧计划的问题不是方向错，而是颗粒度不够。

旧计划能覆盖：

- 产品事实源；
- 技术栈；
- Web 入口；
- Skill 系统；
- Agent runtime；
- Project / Ontology / Workspace；
- Memory / Cognitive / Collaboration；
- Desktop；
- OpenSpec 和测试。

但它不能承诺“吃透整个项目”，原因是：

- 章节太少，无法覆盖 2000 多个文件的真实分布；
- 只列目录，不等于读懂目录里的职责差异；
- 没有把每节课和具体文件桶绑定；
- 没有明确哪些文件精读、哪些通读、哪些索引；
- 没有足够实战来训练定位、修改、测试和变更治理。

## 2. 本次重新扫描依据

本次重新设计课程前，先做了全仓逐文件扫描和文本读取。

扫描结果：

| 指标 | 数量 |
| --- | ---: |
| 全仓文件总数 | 2232 |
| 可读文本文件 | 2097 |
| 可读文本总行数 | 434145 |
| 图片或二进制资产 | 36 |
| `.git`、依赖、构建产物等排除登记项 | 85 |
| 二进制或不可按 UTF-8 读取文件 | 14 |

这意味着深入课程不能只按“主线流程”组织，还必须按“文件覆盖”组织。

## 3. 新课程是否足够

新的课程结构是：

- 72 节源码课；
- 4 个综合实战；
- 每章统一使用 `问题 -> 图解 -> 源码入口 -> 调用链 -> 关键类型 -> 测试入口 -> 练习 -> 验收`；
- 每章绑定文件覆盖范围；
- 每阶段结束要能做定位、画图、读测试和解释边界。

它比旧计划更接近“吃透项目”，但仍要诚实区分三种程度。

### Level 1：能看懂主线

标准：

- 知道 OriginOS 是什么；
- 能说清 Web、Core、Desktop、Agent、Skill、OpenSpec 的大关系；
- 能读懂主要流程图。

宏观 12 课可以达到。

### Level 2：能定位源码

标准：

- 给一个问题，能判断应该看哪个目录；
- 能从 UI 追到 API、core、storage 或 Agent；
- 能找到对应测试和 Story 文档。

24 节主线课可以达到。

### Level 3：能读懂核心模块

标准：

- 能精读 `page.tsx`、`SkillDialog`、Agent session API、`OriginOSAgent`、tools、Project Agent、Ontology store、Memory core、Collaboration runtime、Electron main；
- 能解释关键类型和调用链；
- 能从测试反推真实行为。

需要 72 节源码课。

### Level 4：能参与修改

标准：

- 能做小到中等改动；
- 能遵守 `AGENTS.md`；
- 能控制 diff 范围；
- 能选择正确测试；
- 能说明风险和验证证据。

需要 72 节源码课 + P1/P2/P3 实战。

### Level 5：能维护项目

标准：

- 能写 OpenSpec proposal/design/tasks/spec；
- 能做跨 Web/Core/Desktop/Agent 的影响分析；
- 能评审依赖方向、测试覆盖、数据格式、发布风险；
- 能归档变更并留下证据。

需要 72 节源码课 + P4 完整 OpenSpec 实战。

## 4. 新计划仍然不能偷换的地方

即使升级到 72 节，也不能说“一定背下每个文件每一行”。

真正合理的目标是：

- 所有文件路径都进入覆盖矩阵；
- 核心文件逐章精读；
- 辅助文件按模块通读；
- 历史文档、运行数据、资产、归档材料索引化；
- 每个核心流程都能画图和追调用链；
- 每个关键模块都能找到测试入口；
- 通过实战证明能改、能测、能解释。

这样课程才不是“看起来很完整”，而是能逐步靠近真正掌握项目。
